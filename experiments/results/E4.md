# E4: designed, costed, and not run

E4 was the longitudinal experiment — the one meant to test the half of the first demand
that E2 could not reach. E2 measured *改 A 壞 B*: given a change, does the tool help find
the files that have to change with it. It came back null. The other half is the one the
demand leads with:

> 立意良善的測試、安全閥、守衛、功能,遺忘後變成災難

A guard whose reason nobody remembers, deleted because deleting it is cheaper than
understanding it. Every E2 agent was fresh and had nothing to forget, so E2 could not
have detected this even if the tool prevented it perfectly.

**This document records the design, the feasibility calculation that was run before the
first agent, and the decision not to spend the agents.** The order matters: a negative
result here ends the project, which is exactly when it is easiest to change the design
until it produces something. So the design was fixed first, then costed against numbers
that already existed.

---

## The design, written before the numbers

A chain of **K = 8 consecutive real commits**, run **sequentially on one checkout**, each
agent inheriting the previous agent's tree rather than a fresh one. Arm A is told
CodeSextant is installed; arm B is not; the arms differ in exactly the paragraph E2's
arms differed in, and in nothing else. The harness commits after each step so the next
agent sees its predecessor's work as history, which is what makes the fence somebody
else's and forgotten.

**The metric, ground-truthed and free of self-report:**

    G0       explained guards at the parent of the first commit
    G_ref    those of G0 still present at the last real commit — the fences real
             developers *kept*
    G_agent  those of G_ref still present in the agent's final tree
    score    |G_ref ∩ G_agent| / |G_ref|

Subtracting the ones real history also removed is what makes it a fair question: a guard
the real commit deleted was supposed to go, and counting it would score an agent for
agreeing with history. Reading the tree rather than asking the agent is the same
discipline E2 arrived at the hard way — its first pilot agent reported 18 tool calls
where the harness counted 31.

**The feasibility check, with the window rule fixed in advance** (the most recent eight
consecutive commits touching Python):

| repo | chain | Python files | `G0` | `G_ref` | kept |
|---|---|---|---|---|---|
| flask | 8 | 83 | 42 | 40 | 95% |
| pytest | 8 | 272 | 785 | 785 | 100% |
| alembic | 8 | 119 | 191 | 191 | 100% |

Plenty of fences for the metric to have something to measure. That is where the design
stopped looking sound, because the next question is not how many fences exist but how
often one is taken.

## What the event rate actually is

Three measurements, none of which needed a single new agent.

**1. E2's forty checkouts are still on disk, and each is a real agent's real change with
a ground truth beside it** — the commit the human made from the same parent.
`experiments/exp21_guard_survival.py` re-reads them for fences instead of companions.

| | with_tool | without_tool |
|---|---|---|
| changes | 20 | 20 |
| changes with ≥1 explained fence in reach | 14 (70%) | 14 (70%) |
| explained fences in reach, median per change | 7 | 7 |
| **kept fences removed or loosened** | **0** | **0** |

569 explained fences sat inside the files these agents edited. **Not one was taken.**

The exposure was not the problem, which is the finding that closes off the obvious
rescue: it is not that the tasks avoided fences. The agents worked among them and left
them alone.

**2. The first pass said 1 of 20, and it was my own metric misreading its own output.**
run_02 and run_36 — both arms of the same alembic task — raised the Python floor from
2.6 to 2.7 while modernising `setup.py`, and `raise NotImplementedError("Python 2.6 or
greater is required.")` became `("Python 2.7 or greater is required.")`. That is the
fence being *tightened*. It was reported as weakened because a `raise`'s rule **is** its
message. See the two defects below; after fixing them the count is zero, and the reason
the count moved is written down rather than the count alone.

**3. How often real history does it**, through the shipped filters, over 581 commits of
flask, alembic and pytest: **20 reports, 3.4% of commits.** exp20 measured the same thing
on agent-written history — this repository's own 101 commits — at **8.9%**, six times the
reviewed-OSS rate, and that is the population the demand is about.

## The arithmetic that stopped it

E2's own cost, measured: **90,283 tokens per agent trial** (median 82,113; 40 trials cost
3.61M tokens and 6.7 hours).

The outcome is paired and binary, so the test is McNemar's, and only **discordant** steps
carry information — steps where one arm took the fence and the other did not. A step
where both arms remove the same fence tells you nothing, and that is not hypothetical:
the one candidate event E2 produced occurred in **both arms of the same pair**.

**Best case for the tool — it prevents the event outright**, so every event is a
discordant pair in its favour. A one-sided sign test needs ≥5 of them (0.5⁵ = 0.031):

| assumed rate per step | steps needed | agent runs | tokens |
|---|---|---|---|
| 8.9% (exp20, agent-written history) | 56 | 112 | **10.1M** |
| 7.5% (E2's 95% upper bound, rule of three on 0/40) | 67 | 134 | **12.1M** |
| 0% (E2's point estimate) | — | — | unbounded |

**Realistic case — the tool halves the rate** (8.9% → 4.5%). Discordant probability
0.126, of which 68% favour the tool; McNemar at 80% power and α = 0.05 one-sided needs 48
discordant steps:

    48 / 0.126 = 382 steps  ->  764 agent runs  ->  69M tokens

The cheapest row of the optimistic table costs **10.1M tokens against a remaining session
budget of about 14.8M** — two thirds of everything left, on a design whose result hinges
on the tool being flawless. The realistic figure is five times the whole budget.

**So E4 is not run.** Not "run and null": *unrunnable at any price this project can pay*,
and the measurements that establish that also bound what it could have found. Even a
perfect fourth mode prevents an event that occurs in at most 7.5% of changes and was
observed in 0 of 40, and there is no evidence it prevents any.

## Two defects the power check found in shipped code

Both were in `engine._removed_guards`, both were invisible to the unit tests because both
fixtures hold exactly one assert and one raise, and both were found by pointing the
measurement at real history instead of a fixture.

**`(kind, name)` does not identify a fence.** An assert's name is the empty string and a
raise's name is its exception class, so every assert in a file shared one key and every
`raise ValueError` shared another. The lookup compared whichever copy happened to be last.
Over the 581 commits, **8 of 14 reports were that** — files going from 2 raises to 7, 6 to
9, and 3 to 2. Fixed by pairing the two images on the full rule first, one for one, and
only then asking what is left over.

**The same key decided "it moved, it did not go".** Any surviving assert in a changed file
suppressed *every* assert removal in it, and any surviving raise of the same exception
class suppressed every raise removal. That filter now applies only to kinds whose name is
an identity (`test`, `threshold`, `allowlist`, `env_switch`, `constraint`); asserts and
raises are followed by their rule and their reason, which is what actually travels with
them. This was masking 14 genuine removals in the same 581 commits.

**And `raise` no longer reports a weakening at all.** Its rule is its message, so every
rewording read as a loosened fence — 8 of 8 in the measurement, plus E2's tightened
version floor. Removing a raise is still reported. `test` was already excluded for the
same shape of reason (exp20: 356 of 420 weakenings were tests being edited normally).

Net effect on the same 581 commits: 14 reports → 20, with the 8 artefacts gone and 14
genuine removals unmasked. Four new tests pin each direction.

## What this says, and what it does not

**It says** the failure this project was started for — a forgotten fence deleted because
deleting it was cheaper than understanding it — is rare enough in a single change that no
affordable experiment can show a tool preventing it. Together with E2's null on companion
finding, both halves of the first demand now have a measured answer, and neither is
positive.

**It does not say** the fourth mode is wrong, or that the event never matters. It fires on
3.4% of reviewed-OSS commits and 8.9% of agent-written ones, its reports survived a
spot-check, and one prevented deletion of a real safety valve can be worth more than a
hundred quiet ones. What cannot be done is *demonstrate* that within this budget, and this
project's own rule is that an undemonstrated benefit is not a benefit.

**One thing measured here is positive and points elsewhere.** exp1's frontend corpus —
run under the same protocol, same controls, held-out repository declared in advance — has
co-change reaching F1 **0.524** on vite (precision 0.809) against 0.14–0.19 on every Python
repository, with all twelve paired comparisons excluding zero. The half of this tool that
reads git does not know what language it is looking at, and it is roughly three times
stronger on a TypeScript monorepo than on the corpus every decision here was made against.
Everything E2 and E4 measured was Python. See `docs/plan.md` §2.
