# CodeSextant 新能力「規範符合度檢查（spec-conformance check）」— 問題定義與對齊

> ⚠ 本檔是**問題定義（紅藍 CBUA 的輸入脈絡）**，不是設計最佳解（輸出）。紅藍 CBUA 跑完的權威設計另存 `規範符合度檢查_紅藍CBUA最佳解_2026-06-24.md`。

## 〇、起源（user 2026-06-24 拍板）

user 看到 Wasp（spec-driven framework）的 Twitter thread 得出核心洞察：**規範散在 `.md` 檔會隨時間漂移、且文檔無法強制應用符合它（只描述、靠 AI 自律遵守）；要把規範變成「TS 強行規定的架構」、編譯器能強制執行、寫錯編不過，AI 才會最大化遵守規則寫碼，代碼管理才變得容易且可行。**

user 拍板**形態 A**（三選一）：**做成 CodeSextant 的能力**——用 TypeScript 寫一份「架構規範定義（spec）」，CodeSextant 唯讀讀任意目標 repo、對照 spec、報出哪裡違反，接回現有 hotspot/health 星圖可視化（違規範節點標紅）。語言 Python→TS 都行，以未來最佳能力與便利為主。

被否決的兩形態：B 獨立 spec-driven 強制層（純 CI typed contract，不掛 CodeSextant）、C 自造完整 Wasp 式全端框架（既有上線專案遷移成本巨大、偏離「成為 CodeSextant 能力」）。

## 一、目標（一句）

為 CodeSextant 設計「規範符合度檢查」能力：**TS 寫的架構規範 → CodeSextant 唯讀跨語言檢查 → 報違反 → 接回星圖可視化 + 接 CI 變 exit≠0 硬強制**，追上並超越業界所有架構治理工具，成為 AI King 代碼治理支柱，補上 WIREDO 最難強制的 W（接線）/ I（母版）兩維 + 代碼規範紅藍 CBUA 的 P4「強制層下沉」。

## 二、CodeSextant 身分鐵律（不可違反，違反即否決）

1. **唯讀導航圖**：不改碼、不擋 commit、永不出「應刪/應合併/必須改」決策；輸出是**線索非決策**，刪改前人工讀碼 + 跑 build/CI。
2. **UNKNOWN 安全閘**：解析器無法確定時誠實標 UNKNOWN，**永不誤報紅燈、永不誤殺**（既有 deadcode 已立此原則）。
3. **輕量本地**：單例 daemon（:8790）多代理共用不混線、中文友善、零雲端零金鑰、MIT 開源、零重依賴。**已拒四陷阱**：embedding 語義搜尋 / LSP 重後端 40 語言 / 符號級編輯 / 圖庫 Neo4j-Cypher。
4. **真強制不歸 CodeSextant 自己**：CodeSextant 是檢查器/可視化器；硬擋（exit≠0）靠把它的輸出接上 CI。它本身不 deny。

## 四、必須繼承的 AI King 代碼規範紅藍 CBUA 結論（2026-06-23 SSOT，不推翻）

1. **強制優先序**：`CI exit≠0（HARD，唯一真可靠）＞ PreToolUse deny（HARD）＞ PostToolUse advisory（只提示不擋）＞ Skill 文字（零強制）`。
2. **L6 天花板**：Claude Code 的 hook 攔不住「已發出的純文字斷言」；真強制唯一出路 = 編譯器/CI 的 `exit≠0`。
3. **能力分級 = advisory + 外部守門員 agent**（harness 無接點，`grep model_capability` concinno/src=0、hooks=0）。
4. **import 全域分層閘 NO-GO**（4.53% 倒置會 0-fire vapor）；正解 = **dependency-cruiser 具名 forbid 4-5 條 + CI 增量（只檢 changed files）**。
5. **不掏空 /code、受控重複**；WIREDO 六維（W接線/I母版/R響應/E可配置/D功能驗證/O可觀測），規範符合度檢查主補 **W + I**。

## 五、設計草案須回答的核心問題

1. **規範定義語言**：TS 怎麼寫架構規範（typed config 像 dependency-cruiser `.ts`？DSL？Zod schema？）；怎麼定義 層級 / 依賴方向 / 命名慣例 / 母版約定 / single-source-of-truth / 禁止 pattern；**TS 規範怎麼套用到非 TS 被檢查 repo（Python/Rust/C#/Go…）**。
2. **檢查引擎**：現有 symbols/references/namegraph/callgraph 能支撐哪些規範（分層/依賴方向/孤兒/命名/扇出）；哪些要新增（架構級 pattern matching）；非主語言走名稱比對 fallback 時檢查信心如何降級守「永不誤報紅燈」。
3. **接回星圖**：違規範視覺映射（節點標紅 / 違規依賴連線）；接 health 維度還是獨立維度。
4. **CI 強制路徑**：唯讀輸出怎麼接 CI 成 exit≠0 硬擋（補 P4）；輸出格式（SARIF / JSON / exit code）；只檢 changed files 增量。
5. **跟 dependency-cruiser 的關係**：取代還是補強？（dependency-cruiser 只 JS/TS；CodeSextant 跨 16 語言 = **獨家賣點「跨語言架構規範檢查」業界稀缺**）。
6. **定位邊界**：架構/結構級規範 vs Semgrep/CodeQL 語句級 linting vs ruff/eslint——CodeSextant 守哪層（呼應既有 deadcode 包 ruff 不自造的決策）。

## 七、紅隊 lens（攻擊方向）

1. **過度工程**：自造規範語言 = 重造 Semgrep/dependency-cruiser/ArchUnit 輪子、輕量定位崩壞。
2. **跨語言誤報**：非 TS repo 名稱比對 fallback → 規範檢查大量假陽性，違「永不誤報紅燈」鐵律。
3. **唯讀身分衝突**：「規範符合度 / enforcer」毀「唯讀導航圖、線索非決策」身分。
4. **vapor 風險**：規範定義沒人寫 / 寫了不接 CI = 又一個 fire-but-no-behavior-change 機制（呼應 handoff_bloat fire 272 次行為沒變的教訓）。
5. **TS 編譯器強制的概念漏洞**：tsc 只能強制 TS；檢查非 TS repo 時 TS spec 只是「配置」非「編譯強制」，user 的「編譯器強制」期待在跨語言場景落空——須誠實處理期待落差。
6. **Goodhart**：規範變指標後被 game（湊規範但架構更爛）。
