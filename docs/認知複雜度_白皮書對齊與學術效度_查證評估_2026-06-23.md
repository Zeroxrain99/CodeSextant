# CodeSextant 認知複雜度查證評估（2026-06-23）

> 起因：交接報告坦承「P3/P4 認知複雜度的規則是基於訓練知識＋子代理 review 時查的開源碼、這回沒上網查證」。user 要一份「對齊白皮書原文／看學術效度／對比 lizard·complexipy·rust-code-analysis」的有引用權威評估，再決定後續。本檔即此查證。

## 〇、一句話結論

CodeSextant 的認知複雜度實作**高度對齊** SonarSource 白皮書與官方語言外掛（language plugin）規則；唯一已知偏差是**間接遞迴漏算**（只算直接遞迴、方向為低估、已誠實標、且有業界先例）。但要認清這個指標的**學術天花板**：它經驗上只證實「部分反映可理解性、尤其理解時間與主觀難易感」，對「理解正確性」預測弱——所以拿它當星圖「找難讀熱點／相對排序」的飽和度維度是用對了，⛔別宣稱它衡量 bug 率或正確性。

## 一、規則對齊表（complexity.py 真碼 vs SonarSource 規範）

對照來源：SonarSource 白皮書（G. Ann Campbell）、官方 Python 外掛規則 S3776、效度論文對規則的複述、SonarSource issue 串。

| 規則 | SonarSource 規範 | CodeSextant 真碼 | 對齊 |
|---|---|---|---|
| B1 基本增量：if／迴圈／switch／catch／三元／帶標籤跳轉 | 每個 +1 | `incr_nest`＋`visit_if`／`visit_if_field`／`visit_if_swift`＋`labeled_jump` | ✅ |
| B2 巢狀層：迴圈／if／switch／catch／**巢狀函數·lambda** 增 nesting level | 增層 | `incr_nest`／`nest_only` 皆 `nesting+1` 往下傳 | ✅ |
| B3 巢狀增量：巢狀結構 `+1+當前深度`；**else／else-if 不拿 B3**（同決策鏈延續） | +nesting | `total += 1 + nesting`；`visit_elif`／else-if 只 `+1` | ✅ |
| method **呼叫**（call）free | 不加分 | `call` 節點只在「直接遞迴」時 +1，其餘不加 | ✅ |
| 巢狀函數·lambda **宣告** | 增 nesting level、**不**加 B1 | `nest_only`＝增層不加分 | ✅（見 §四爭議） |
| 連續邏輯運算子：`a&&b&&c`=1、`a&&b‖c`=2（混用才多算）、**不增層** | per run +1 | `count_bool_runs`＝數相鄰不同 run、最外層算一次、不增 nesting | ✅ |
| null-coalescing `??`（C#）／`?.` | **不**算（白皮書明文 ignore） | `bool_ops` 只收 `&&`/`‖`、刻意排除 `??`（程式碼註解明標、對抗 review HIGH 修） | ✅ |
| 遞迴 | 算（白皮書含**間接/相互遞迴**）每個 +1 | **只算直接遞迴**（裸名==func_name 或 self/cls/this.func_name） | ⚠ 漏間接（低估）、誠實標 |

真碼旁證（complexity.py）：`visit_if` 第 510 行 `total += 1 if as_elseif else (1 + nesting)`＝else-if 只拿 B1、首 if 拿 B1+B3，完全吻合白皮書「else-if 不拿 nesting increment」。`count_bool_runs`（407 行）數「相鄰不同運算子的 run 數」＝白皮書「sequences of binary logical operators」的精確語意。

## 二、學術效度（這是「該不該信這指標」的硬證據）

**主來源**：Muñoz Barón, Marvin; Wyrich, Marvin; Wagner, Stefan.《An Empirical Validation of Cognitive Complexity as a Measure of Source Code Understandability》，ESEM 2020（ACM/IEEE 第 14 屆實證軟體工程與量測研討會）。arXiv:2007.12520。**規模**：系統性文獻彙整 9 份研究、約 **24,000 筆可理解性評估、427 個程式碼片段**、做 meta 分析（統合分析）。

效度數字（加權平均相關係數 r）：

| 對什麼的相關 | r | 效果量 | 解讀 |
|---|---|---|---|
| 理解**時間**（comprehension time） | **0.54** | 大正相關（最強） | 複雜度越高、越花時間讀懂 ✅ |
| 主觀**理解難易**評分 | **−0.29** | 中負相關 | 方向對：越複雜、主觀越覺得難 ✅ |
| 複合變數（composite） | 0.40 | 中正相關 | — |
| 理解**正確性**（correctness） | −0.13 | 小、**混合**（範圍 −0.52~+0.57） | 弱、不穩 ⚠ |
| 生理測量（fMRI 等） | 0.00 | 無相關 | 樣本僅 12，幾無證據 |

**作者結論（誠實版）**：認知複雜度是「**第一個**經驗驗證、純基於代碼的可理解性指標、能反映**至少部分**面向」；但「**並未**達成『顯著優於先前指標』的承諾」（就「預測可理解性」這件事而言）。

→ 對 CodeSextant 的意義：用它做「**相對排序、找難讀熱點、看哪個函數讀起來費時**」站得住腳（理解時間 r=0.54 是強證據）；把它接成星圖飽和度（褪色＝相對更難讀）＝**正確用法**。但⛔別把它當「正確性／bug 風險」指標（correctness r 僅 −0.13 且混合）。

## 四、唯一真正的爭議點：巢狀函數增不增 nesting（已查清）

這是查證中最值得釐清、也是一個**證據矛盾**處，誠實記錄：

- **抓取 sonar-python S3776 時**，小模型回「Nested functions do NOT increment nesting」，理由「method calls are free」。
- **判定＝小模型誤讀**：它把「**呼叫** method 免費（call free）」誤套成「**巢狀函數宣告**不增層」。兩者是不同規則。
- **反證（硬）**：SonarSource issue #2288《Cognitive Complexity score should not penalize with nesting for C# local functions》原文——「Currently the rule S3776 **intentionally penalizes C# local functions with a +1 for nesting**」。報告者是來**抱怨**這個增層、想移除它，恰恰證明 SonarSource 官方實作**確實對巢狀/local function 增 nesting**。
- **效度論文複述**也支持：巢狀結構 `+1+深度`、結構越深加越多。

**定論**：原始白皮書與 SonarSource 主流實作＝巢狀函數/lambda **宣告增 nesting level、不加 B1**。CodeSextant `nest_only`（增層不加分）＝**對齊**。

**唯一可討論的現代化分歧**：社群（issue #2288）有「local function 不該被 nesting 罰」的訴求，部分 sonar-dotnet 版本後續對 top-level local function 做了豁免。CodeSextant 採「一律增層」＝對齊**原始**白皮書，比「最新 sonar-dotnet 對 local function 豁免」**略嚴**。這是 cosmetic 級可選調整（要不要對最外層巢狀函數豁免增層），**非錯誤**。

## 五、結論與後續決策支援

**1. 對齊度判定＝高**。B1/B2/B3、boolean run、`??` 排除、method call free、巢狀函數增層——逐條對齊 SonarSource 白皮書與官方外掛。黃金案例 `sumOfPrimes=7`（白皮書招牌範例）pytest 已驗，是最強的端到端正確性錨點。

**2. 已知偏差只有一個＝間接遞迴漏算**（只算直接遞迴）。方向為低估、已誠實標 UNKNOWN/限制。且有業界先例：sonar-cxx issue #1271 同樣討論「因辨識真遞迴呼叫的假陽性而縮水遞迴增量」——CodeSextant 的保守選擇站得住。要補也只是錦上添花，非修 bug。

**3. 認清效度天花板**。學術只證「部分有效、偏理解時間/主觀感」。CodeSextant 把它當星圖飽和度（找難讀熱點、相對排序）＝用對；⛔別宣稱衡量正確性/bug 率。

**4. 可選的精修方向（皆非急、非錯誤修補）**：
   - (a) 間接/相互遞迴：補上可更貼白皮書，但假陽性風險高、CP 值低。
   - (b) 最外層巢狀函數豁免增層：追最新 sonar-dotnet 行為，cosmetic 級、要不要看偏好。
   - (c) 擴 P5 仍 UNKNOWN 的語言已在做（complexity.py 實物已含 C/C++/Ruby/Kotlin/Swift，超出交接記載的 8 語言、版本號待 bump）。
   - (d) 維持現狀：對齊度已足、效度本身有天花板，再投入邊際效益遞減。

**四個結論（含一個誠實的反直覺發現）**：

1. **指標有區分力**：兩 repo 中位數都是 2（多數函數簡單），但尾端（p90/max）拉得開——證明認知複雜度能精準定位「少數難讀熱點」，正是學術上 r=0.54（理解時間）最強的用法。
2. **指標誠實不偏袒**：全場最高 cog=335 的熱點是 CodeSextant **自己的** `complexity.py:360 cognitive_complexity`（那個算認知複雜度的巨型 walker、把所有 `visit_*` 當閉包塞一個函數內）——工具老實把自己最難讀的函數標出來、不護短。人眼複核方向正確（本場讀過該函數 721 行、確實是全 repo 最難讀的）＝ground truth 對齊。
3. **反直覺但真實**：原假設「CodeSextant 乾淨 vs concinno 屎山」被數據推翻——concinno 雖大 4848 函數，但拆得細、平均反而更低（4.80）；CodeSextant 小但有幾個巨型 walker 函數把平均拉高（8.41）。這是查證精神的勝利：不腦補、讓數據說話。
