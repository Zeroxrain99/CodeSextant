A performance and correctness release, from a report that a machine was struggling.
Finding the cause led to a defect in this tool's own headline claim, and both are here.

## Install

```bash
pip install https://github.com/Zeroxrain99/CodeSextant/releases/download/v0.30.0/codesextant-0.30.0-py3-none-any.whl
```

## The watcher was watching your whole disk

The filesystem watcher asked watchdog for `recursive=True` over the repository root
with **no exclusions at all**. Grepping `watcher.py` for `SKIP`, `ignore`,
`node_modules` or `.git` returned nothing. The indexer has had a skip list for build
and dependency output since the first commit; the watcher never used it.

On a tree shaped like a real project — 609 directories, 25 of them source, the rest
`node_modules`, `.venv` and `build`:

| | before | after |
|---|---|---|
| directories watched | 609 | **27** (4.4%) |
| attach time | — | 50 ms |

On Linux those are inotify descriptors against a cap that is **per user**, so
exhausting it breaks every editor and build tool on the machine rather than just this
one. Everywhere else it is an event storm on every `npm install`, waking a debounce
timer for files this tool will never read.

The tree is now walked with the indexer's own skip list, and the walk is used on the
backends that charge per directory. FSEvents and ReadDirectoryChangesW do the recursion
in the kernel, where one scheduled path covers the subtree and pruning would cost more
than it saves — that half was wrong in the first version of the fix and every macOS CI
job said so. The **event filter is not conditional**: build output is ignored on every
platform, because the storm is what wakes the timer regardless of how the watch was
obtained.

`CODESEXTANT_WATCH_MAX_DIRS` (4,000) makes the watcher stop adding rather than exhaust
a system limit.

## `codesextant stop`

Until now the only ways to get the background process off a machine were to wait out a
three-hour idle timeout or find the PID. Neither is an answer a tool should make its
user give.

```bash
codesextant stop
```

It waits for work already in progress to drain, says so if it is still draining rather
than reporting a state that is not yet true, and exits non-zero if a daemon is still
resident. **A refusal is not an absence**: a daemon that rejects the request proof is
reported as running, not as absent.

Three defects surfaced while testing it:

- **After `stop`, the daemon could not restart for about a minute.** `SO_REUSEADDR` was
  disabled from a Windows fact read as a general one. On POSIX it does not permit two
  live listeners — only `SO_REUSEPORT` does, and that stays off everywhere — it only
  permits binding over a TIME_WAIT socket whose process has exited. Measured: `stop`,
  then three restart attempts over three seconds, all `spawn-timeout`.
- **"Address already in use" surfaced as an `AttributeError`** about an internal name,
  because teardown ran before `__init__` had finished.
- **"Stopped" was reported while the process was still draining**, so the next command
  met a refusal from the daemon that had just been stopped.

## `preflight` missed a duplicate in the file you have open

`preflight --symbol shutdown` answered *"nothing resembles it; it looks new"* while
`initiate_shutdown` was indexed in that very file. The reuse check required two shared
words, so a one-word query could only ever match exactly.

That rule was deliberate and its reason was real — one shared word is usually a common
verb. It was also decided by eye. Measured over **408 shape-duplicates in six
repositories**, allowing a single shared word when the word is rare in the tree and the
overlap still clears the threshold reaches **+0.014 more duplicates on the held-out set
for one extra name every twenty queries**.

Three costlier variants were measured and refused, including one that read 143 names
per query. `CODESEXTANT_PREFLIGHT_RARE_WORD_MAX` moves the gate; `0` turns single-word
matching off.

## Everything else

- `CODESEXTANT_STOP_DRAIN_SEC` (10) bounds how long `stop` waits for in-flight work.
- The idle timeout stays at three hours. It was measured rather than assumed: an idle
  daemon holds 30–36 MiB and burns 0.02% of one core, against a 0.22 s cold start. The
  lag had a different cause.
