# CodeSextant 計畫:目標、判準、與防跑偏機制

這份文件管三件事:**要解決什麼**、**憑什麼說解決了**、**什麼時候該停手**。
`docs/roadmap.md` 是工項清單,這份是它服務的目標與紅線。兩份不一致時,以這份為準。

---

## 一、兩條需求(逐字,不得改寫)

> **1.** 解決我真實遇到的 AI 編碼問題 — 立意良善的測試、安全閥、守衛、功能,遺忘後變成災難:重造輪子、浪費時間和 token 修復、改 A 壞 B。
>
> **2.** 成為 SOTA。

第二條**從屬於**第一條。一個在基準測試上贏、但不解決第一條的功能,不算 SOTA,算 過度工程。

---

## 二、七個問題,現況要誠實

「有跟沒有差不多的垃圾」的判準只有一個:**每一格都有一個在 held-out 集上量到的數字**。
沒量過的寫「未測」,不寫形容詞。

| 問題 | 現在靠什麼 | 量到了什麼 | 缺口 |
|---|---|---|---|
| **改 A 壞 B** | co-change(讀 git)+ blast radius(jedi 解析) | 檢索層有數字;**但 E2 顯示這些數字沒有轉成任務結果的差別** | 前端解析未量(見下);而且檢索變好不等於結果變好 |
| **遺漏** | `check` 四個模式:三個問「你忘了加什麼」,第四個問「你拿掉了什麼」 | **E2 量到:20 對裡 20 對,有無工具找到的伴隨檔案完全相同** —— 前三個模式對「找到什麼」沒有影響。第四個模式 E2 沒測到,因為它的 20 個任務全是「做這個改動」,沒有一個是「這裡有個看起來多餘的柵欄」 | 第四個模式只在**這個 repo 自己的歷史**上量過(8.9%),沒有 held-out 的 agent 語料可以確認 |
| **重造輪子** | `preflight --symbol` 的重用評分 | exp16:held-out 0.408,三個更貪心的變體都量過才選 | 跨語言、跨檔案內的重用未涵蓋 |
| **大海撈針** | symbol 搜尋、`map` | 未測 | 沒有自然語言/關鍵字入口 |
| **檢查接線** | `references`、`impact` | 解析後的邊有效;名稱邊會淹沒排序,已修 | 設定檔、路由、DI、跨行程的接線沒有模型 |
| **簡易除錯** | `guards`(六種柵欄) | 兩層曾被目測否決,量完是 **+0.100 held out**,兩層都該建 | — |
| **過度工程** | **什麼都沒有** | — | 見第五節。這是唯一一個「使用者的要求本身就是風險」的欄位 |

**最大的一格是語言 —— 這句話寫下來的時候沒有數字,量完之後要改。**

原本的推論是:解析是 Python-only,其餘十二種語言退化成名稱比對,使用者的痛點又全在
TypeScript/React,所以工具在那裡最弱。**推論的前半對,後半錯了。**

co-change 讀 git,根本不知道自己在看什麼語言,所以它可以直接量。exp1 在新宣告的前端語料
(express、zod,held-out 的 vite)上跑同一套協定、同一組對照組:

| | precision | recall | F1 | 對上同預算最強對照組 |
|---|---|---|---|---|
| Python (requests/click/tqdm) | 0.49–0.55 | 0.08–0.11 | 0.141–0.177 | +0.054 ~ +0.066 |
| express | 0.736 | 0.220 | 0.339 | +0.085 |
| zod | 0.622 | 0.111 | 0.188 | +0.137 |
| **vite**(held out) | **0.809** | **0.387** | **0.524** | +0.058 |

前端語料 **12 個配對比較全部排除零**;Python 語料有 4 個沒有。
**vite 是兩組語料裡最強的一個**,而 vite 正是「多個套件必須一起動」的 monorepo ——
就是你那個「網頁版和 VS Code 擴充必須同構」的形狀。

所以 P0-1 要改寫:**不是「趕快補 TS/JS 解析」,而是「先量解析在 TS/JS 上還能多加多少」。**
已經在跑的那一半在那裡表現比 Python 還好;要加的那一半值多少,現在一個數字都沒有。
**這正是規則 1(先量後建)—— 而這次被它擋下來的是我自己寫在這份文件裡的 P0。**

還沒被推翻的部分要照樣說清楚:這只量了 preflight 三根柱子裡的**一根**。
blast radius 在 TS/JS 上仍然只有名稱比對,而且**完全沒有量過**。

## 三、關於「知識圖譜」:對的部分與錯的部分

使用者的提案:自動把有關連的都連起來、可以自己上備註、關鍵字好查、
「關聯最多的代碼應該都要寫跟 199 個代碼相關連」、能直接查跟誰有關。

**對的三件事,直接採納:**

1. **自動、完整** — 不能靠人記得登記。這正是需求 1 的核心:靠記憶的守衛一定會忘。
2. **可註記** — 目前**完全沒有**。這是最便宜、最直接命中需求 1 的缺口,見第四節 P0-2。
3. **可反查** — 「誰跟我有關」必須是一個問句,不是一次全域搜尋。

**一件要改的事,而且這個專案已經量到證據:**

「跟 199 個代碼相關連」這種**度數統計沒有用**,而且會主動有害。

- 這個專案修過一次同樣的病:低信心的名稱邊曾經淹沒排序(roadmap 1b),必須降權才可用。
- E2 的評分器也量到同一個形狀:一個**把每個 Python 檔都改一遍**的 shotgun baseline,
  在 `changed_a_broke_b` 和 `forgot_the_guard` 上都拿 **1.00**。高召回、零精確,分數滿分,毫無用處。

所以規則是:**圖要建全,呈現要少而準,而且必須排序。**
一個回答「199 個」的工具,和一個回答「這 3 個,理由分別是 A/B/C」的工具,前者是雜訊產生器。
圖的完整性是**內部**指標;對外的每一個答案都要能說出「為什麼是它」。

## 四、分期

每一期的完成定義都是**一個 held-out 數字**,不是「做完了」。

### P0(擋住真實痛點)

1. **先量 TS/JS 解析值多少,再決定要不要做。**(原本寫的是「補上 TS/JS 解析」,量完 co-change
   之後改成這樣 —— 見第二節。)
   第一步是把 exp2 的協定跑在前端語料上,得到 blast radius 在 TS/JS 上的現況數字。
   要做的完成定義:在 held-out 的 vite 上,`co-change + 解析` 的配對差要**顯著優於 co-change 單獨**,
   用同一套評分程式,不另立標準。**如果差不出來,這一項就進拒絕清單,不進 roadmap。**
2. **`check` 的第四個模式:你拆掉或放寬了一個有人寫下理由的柵欄。**(原本寫的是
   「加一套註記機制」,exp20 量完之後改成這樣。)

   **註記的儲存不用蓋,已經存在。** `guards.stated()` 已經會從 docstring、上一行註解、
   `assert`/`raise` 的訊息裡把理由抓出來,還記錄來源。而 exp8 早就警告過:
   手維護的登記簿(ADR、feature-flag inventory)一定會過期 —— 理由寫在柵欄旁邊才不會漂。
   **缺的不是存放處,是 `check` 沒有在看。** 它現有三個模式全部在問「你忘了加什麼」,
   **沒有一個在問「你拿掉了什麼」。**

   exp20 量了 1,382 個真實 commit,而**結論取決於是誰寫的 code**:

   | | 六個 OSS repo(1,382 commit) | 這個 repo,agent 寫的(101) |
   |---|---|---|
   | 拆掉一個**有理由**的柵欄 | 21 次 — **1.5%** | 9 次 — **8.9%** |
   | 被拆的柵欄裡有理由的比例 | 35% | 48% |
   | 被拆的種類 | 幾乎全是 `test` | `env_switch` 6、`assert` 6、`allowlist` 3、**`threshold` 2** |
   | `threshold` 被放寬 | **1,382 個 commit 裡 0 次** | 有 |

   **在有人 review 的成熟 OSS 上,這個模式一年也響不了幾次,而且響的幾乎都是刪掉的測試。
   在 agent 寫的歷史上,頻率高六倍,而且打中的正是安全閥那幾種。**
   這就是需求 1 描述的那件事,而它在 OSS 語料上量不到 —— 因為 review 擋掉了。

   兩個必須一起說的保留:**(a)** 那 101 個 commit 就是這個 repo,主要是我自己寫的,
   所以它同時是最相關、也最不獨立的樣本 —— 是推導觀察,不是 held-out 確認;
   **(b)** 原本最想抓的案例(`MAX = 250` 被偷偷改成 5000)在 OSS 語料**一次都沒發生**,
   所以那個設計動機是我想像的,不是量到的。
   把 `test` 的「放寬」讀成訊號也不行:測試的 rule 只要 body 改了就變,
   420 次放寬裡 **85% 是測試**,那是雜訊;非測試的只有 64 次、有理由的 27 次。

   完成定義:在 agent 寫的歷史上重放,對真的被拆掉的有理由柵欄要命中,
   對改名和搬家要沉默(exp20 已量到:不排除改名的話,183 次「移除」裡有 **108 次是搬家**)。
3. **E2 跑完** — 見第六節。沒有 E2,前兩項的價值只是推論。

### P1(把接線補完)

4. **設定與路由的接線** — 路由表、DI 容器、環境變數、build 設定。
   這是「改 A 壞 B」在框架型專案裡的主要形狀,而目前的模型完全看不見。
5. **關鍵字 / 自然語言入口** — 大海撈針。
   完成定義:在 held-out 問句上,前 5 名命中率要贏過 `grep`。贏不過就不做。

### P2(競品調查,先量後建)

6. **SOTA 功能盤點** — 產出一張表:功能、競品、**在我們的評測集上量到多少**、成本。
   **不是「都要補上」。** 補的順序由第二節的七個問題決定,不由競品的功能清單決定。
   一個競品有、但對七個問題沒有數字的功能,寫進「拒絕清單」,不寫進 roadmap。

## 五、防跑偏:五條可檢查的規則

「隨時防止跑偏」不能靠自律,要靠**會失敗的檢查**。

1. **先量後建。** 任何候選功能在寫第一行實作前,先在既有的 dump 上評分。
   exp6 用這個方法以一次執行的成本否決了四個候選。
   *目測否決也是假設* — `guards` 的兩層曾被有理有據地否決,量完發現兩層都該建(+0.100)。
2. **推導集 / held-out 集分開,永不對調。** 規則在 requests/click/tqdm 上推導,
   在 jinja/httpie/rich 上確認。反過來做的數字一律作廢。
3. **控制組和真答案用同一支程式排序。** 否則量到的是排序程式的差異,不是功能的差異。
4. **拒絕清單和 roadmap 一樣重要。** 每一個沒做的東西,要寫下**理由和當時的數字**。
   `HANDOFF.md` 的「What was tried and refuted」就是這個清單,只能增,不能刪。
5. **資源上限是測試,不是承諾。** 見第七節。超過就是紅燈,不是「之後最佳化」。

**還有一條給我自己的:** 每一個宣稱都要能指到一個檔案或一次執行。
這個專案已經有兩次 commit message 宣稱改了 `HANDOFF.md` 而實際沒改,
一次對使用者回報「還有 2 個代理在跑」而實際是 0 個。
**沒有證據的進度回報,比沒有回報更糟。**

## 六、E2 跑完了,結果是:量不到差別

> **事後稽核修正了這一節的「原因」,結論不變。** 重跑當時的 preflight 對照答案:
> agent 自己找到 40/60 個伴隨檔案,**工具只點名 5/60(8%)**;八個沒拿滿分的 with_tool
> trial 裡,工具對漏掉的檔案**一個都沒點名**。答案集合裡 43% 是 CI/相依設定(工具 0/26)、
> 22% 是 release note(其中 9 個在 parent 根本不存在)。
> **所以這個 null 在第一個 agent 跑之前就決定了。** 完整分析與數字在
> [`docs/audit.md`](audit.md);下面這一節保留原樣,因為它是當時記下來的東西。

E2 是唯一一個直接回答「這工具到底有沒有幫到人」的實驗:同一個任務、同一個模型,
一組有工具、一組沒有,配對比較 token 與品質。

**20 對、40 個 trial、361 萬 token、零汙染。結論:品質和成本都量不到差別。**

**品質那一格不是「沒差」,是「一模一樣」。**
20 對裡有 **20 對,兩邊改到的真實伴隨檔案是完全相同的集合** —— 不是數量相同,是同一批檔案。
其中 11 對改動的檔案集合確實不同,但差異全部落在真實答案之外,
所以三個模式的差都是 0.000、區間寬度是零。這是恆等,不是被雜訊蓋掉的空值。

**成本那一格量不到。** 合併後 **−5.4%(−5,052,區間 [−14,158, +2,711])** —— 區間含零,
而且符號檢定是 **11 對省、9 對貴**,接近擲硬幣。每對差的標準差是 **19,537 token,
是它要解析的平均值的 3.9 倍**。

| 分層 | 差(token) | 95% 區間 | 排除零 |
|---|---|---|---|
| 合併(20) | −5,052(−5.4%) | [−14,158, +2,711] | 否 |
| convention(7) | −14,750 | [−35,285, +1,944] | 否 |
| grep_reachable(7) | −2,308 | [−8,818, +4,890] | 否 |
| **hidden(6)** | **+3,061** | [−7,460, +13,600] | 否 |

**`hidden` 是這個工具存在的理由,而它的點估計方向是反的。** 六對定不了案,
但那是設計預期的相反方向,照實記下,不解釋掉。

**工具確實被用了:71 次呼叫(preflight 23、guards 25、check 23),20 個 arm 全部有用;
沒工具那組沒有任何一個摸到 binary。** 所以這不是「工具被忽略」。

**pilot 的「多花 14.4%」正式撤回。** 那九對同時帶著兩個錯:checkout 裡有答案,
而且 shim 沒有 export `CODESEXTANT_HOME`,所以每個 with_tool arm 都在自己的預算裡
重建了一次索引。兩個都修掉之後,方向反過來了。

**要多少對才問得出來:** 以量到的變異,80% 檢定力要偵測 5.4% 需要 **118 對**,
10% 需要 35 對,20% 只需要 9 對。**也就是說:大效應會在這 20 對裡現身,而它沒有。**

完整寫法與所有保留條件在 `experiments/results/E2.md`。

**這一段的方法教訓,比結果本身更該留下:**
一個沒有事先斷言隔離的實驗,跑完就是白跑 —— 這件事在這個專案發生了兩次。
第一次是 `git worktree` 共用 object store;第二次是「隔離 checkout ≠ 隔離 trial」,
受測 repo 是公開的、任務指示就是上游 commit message、容器有網路,
前八個 trial 就有三個從網路把答案抓回來。**花代理之前先驗隔離,不是之後。**

## 七、E4:設計了、算了成本、決定不跑

E4 是要回答需求 1 前半段的實驗 —— E2 量的是「改 A 壞 B」,而需求開頭那句
「立意良善的測試、安全閥、守衛、功能,**遺忘後變成災難**」E2 量不到:
它每個 agent 都是全新的,沒有東西可以遺忘。

**負面結果會終止這個專案,那正是最容易作弊的時候。所以設計先寫死,再拿既有數字去算成本。**

設計:K=8 個連續真實 commit,**在同一個 checkout 上依序跑**,每個 agent 繼承前一個 agent 的樹。
指標是 ground truth,不靠自述:`G_ref` = 真實開發者**留下來**的有理由柵欄,
分數 = agent 最後那棵樹裡還留著的比例。可行性算過了,柵欄數量夠(flask 40、pytest 785、alembic 191)。

**然後量事件率,一個新 agent 都不用花 —— E2 的四十個 checkout 還在磁碟上,
而且每一個旁邊都有 ground truth(同一個 parent 上人類真正做的那個 commit)。**

| | 有工具 | 沒工具 |
|---|---|---|
| 改動數 | 20 | 20 |
| 手上有 ≥1 個有理由柵欄的改動 | 14(70%) | 14(70%) |
| 伸手可及的有理由柵欄(合計) | ​569 個 | |
| **拆掉或放寬了真實歷史留下的柵欄** | **0** | **0** |

**曝險不是問題** —— 這堵住了最明顯的辯解。不是任務剛好避開柵欄:
agent 就在柵欄中間工作,然後沒動它們。

第一輪跑出 1/20,**那是我自己的指標讀錯自己的輸出**:run_02 和 run_36
(同一個 alembic 任務的兩個 arm)把 Python 下限從 2.6 提到 2.7 —— 那是**收緊**柵欄 ——
卻被報成放寬,因為 `raise` 的 rule 就是它的訊息。修掉之後是 0。

**檢定力算術。** 配對二元結果只有**不一致**的步數帶資訊,而 E2 唯一那個候選事件
**發生在同一對的兩個 arm 上**。E2 實測每個 trial 90,283 token。

| 假設每步事件率 | 需要步數 | agent 次數 | token |
|---|---|---|---|
| 8.9%(exp20,agent 寫的歷史)且**工具完美** | 56 | 112 | **1,010 萬** |
| 7.5%(E2 的 0/40 三法則上界)且**工具完美** | 67 | 134 | **1,210 萬** |
| 8.9% 且工具把事件率**減半**(現實情況) | 382 | 764 | **6,900 萬** |

最樂觀那一列要吃掉這個 session 剩餘預算(約 1,480 萬)的三分之二,
而且結論取決於「工具零失誤」。現實那一列是整個預算的五倍。

**所以 E4 不跑。不是「跑完是空的」,是在這個專案付得起的任何價位上都跑不出結論** ——
而且證明這件事的那些量測,同時也框住了它最多能找到什麼:
即使第四模式完美,它擋的是一個在 ≤7.5% 的改動裡發生、而四十個改動裡觀察到 0 次的事件。

**順帶抓到兩個已出貨的真缺陷**(細節見 `experiments/results/E4.md`):
`(kind, name)` 不是柵欄的身分(assert 的 name 是空字串,raise 的 name 是例外類別),
581 個真實 commit 的 14 個報告裡 **8 個是同檔案內 key 碰撞的假象**;
同一個 key 還被拿去判斷「只是搬家」,**掩蓋了 14 個真實移除**。都修了,四個新測試各釘一邊。

## 八、裁決:暫停,以及暫停的是什麼

使用者的話:「跑完這個 如果還是沒用 這項目就暫停」。

> **這一節的措辭已被 [`docs/audit.md`](audit.md) 修正。** 正確的說法不是「量不到幫助」,
> 而是**「用一個瞄錯的實驗,量了一個在該處本來就沒有能力的工具」**。暫停的決定不變,
> 但回來時的第一步因此改變:不是加功能,是先用零 agent 成本量工具自己的召回率。

**需求 1 的兩半現在都有量到的答案,兩邊都不是正面的:**

| | 實驗 | 結果 |
|---|---|---|
| 改 A 壞 B(找伴隨檔案) | E2,20 對、361 萬 token | 品質 20/20 對**完全相同**;成本 −5.4%,區間含零 |
| 遺忘柵欄被拆掉 | E4,零 agent 成本的檢定力分析 | 四十個改動、569 個伸手可及的柵欄、**0 次事件**;任何有檢定力的版本都超出預算 |

**要誠實說清楚暫停的是哪一條路:所有這些量測都是 Python。**
而 exp1 在前端語料上量到的東西方向相反 ——
co-change 在 vite(held-out 的 TS monorepo)上 F1 **0.524**、precision 0.809,
Python 語料是 0.14–0.19,**十二個配對比較全部排除零**。
讀 git 的那一半不知道自己在看什麼語言,而它在 TS monorepo 上大約強三倍。

所以暫停的是:**在 Python 單一 repo 上繼續加功能**。
還沒被否定、而且量起來便宜(不需要 agent)的是 P0-1:
把 exp2 的協定跑到前端語料上,看解析那一半在 TS/JS 上值多少。
使用者最初的痛點本來就是一個 TypeScript 前端跟它的 VS Code extension 走散 ——
這個專案從頭到尾沒有在那個語言上量過任何東西。

## 九、資源上限(超過即紅燈)

使用者的話:「不能太消耗電腦資源,不然跑不動不如不跑」、「不能每一次使用都要重建一次索引」。

| 項目 | 現況(已量) | 上限 |
|---|---|---|
| 閒置記憶體 | 30–36 MiB | 不得超過 100 MiB |
| 閒置 CPU | 一顆核心的 0.02% | 不得超過 0.5% |
| 檔案監看數 | 修正後 27/609(修正前監看了 98.3% 無用目錄,會卡住機器) | 預設上限 4000 目錄,可用環境變數調 |
| 重建索引 | 增量;co-change 只在 HEAD 移動時重新開採 | **永不全量重建**,除非使用者明確要求 |

「卡電腦」曾經是這個工具最嚴重的真實問題,原因是監看器監了 98.3% 沒用的目錄。
已修,並在 0.30.0 從公開發布網址重裝驗證過。這一列的意思是:**這種事不准再發生第二次。**

## 十、這個計畫怎麼用

- 開任何一個新工項前,先問:**它對應第二節的哪一個問題?** 對不上就不做。
- 宣稱完成前,先問:**held-out 的數字是多少?** 沒有就是沒完成。
- 覺得某個功能「明顯該做」或「明顯不該做」的時候,那是假設,去量。
- 想「順便都補上」的時候,回頭看第二節最後一列。
