# 解析覆蓋率量測基線（2026-07-19）

CodeSextant 一直只在**單次查詢**裡自述可靠度（`reliability` 欄位）。這份文件補的是
另一個問題：**整體到底解得動幾成**——一個離線可重跑、可比較、可被打臉的數字。

重跑指令（固定種子，任何人跑都拿到同一組樣本）：

```bash
python tools/measure_coverage.py --project <repo 絕對路徑> \
       --path-contains <產品碼目錄> --sample 25
```

## 本次結果（量測對象＝CodeSextant 自己）

| 範圍 | 語言 | 符號 | 名稱級候選 | 高信心 | 低信心 | 解析率(中位) | 解析率(加總) | 零高信心 | 秒/符號 |
|---|---|---:|---:|---:|---:|---:|---:|---:|---:|
| 產品套件 `codesextant/` | python | 25 | 163 | 58 | 21 | **50.0%** | 35.6% | 44.0% | 0.29 |
| 全 repo（含實驗腳本） | python | 21 | 678 | 29 | 578 | 0.0% | 4.3% | 52.4% | 0.57 |
| 全 repo | typescript | 4 | 21 | 8 | 6 | 50.0% | 38.1% | 25.0% | 25.3 |

## 這些數字怎麼讀（⛔ 別直接拿去跟別人比）

**解析率的分母對工具不利，這是刻意的。** 分母是純文字掃描的名稱級命中數，裡面本來
就混著同名雜訊——註解、字串、別的類別的同名成員。所以它**不是準確率**，而是「面對
名稱級的一團模糊，工具能斬釘截鐵確認多少」。選這個定義正是因為分母由純文字掃描
決定、跟工具無關，**沒辦法靠調整分母灌水**。

**中位數和加總差很多，那個差距本身就是情報。** 加總會被 `project`、`main` 這種到處
都是的通用參數名主導：單一個 `project` 就貢獻 479 個名稱級命中，其中絕大多數是別的
函式的參數、跟這個符號一點關係都沒有。中位數才反映「對一個一般的符號解得動多少」。
兩個都報，不挑好看的那個。

**「零高信心 44%」不等於失敗。** 對外公開 API（被 repo 外部消費）、CLI 入口、測試
專用符號，本來在 repo 內就沒有呼叫者——零高信心是正確答案。要判斷得逐個讀碼。

## 量測方法本身踩過的三個坑（都寫進碼裡防再犯）

做這份基線的過程比結果更有教育意義：**同一份工具、同一份 repo，因為測法不同，數字
從 2.0% → 4.3% → 50.0%。** 三次都是測法錯，不是工具變好。

1. **用 `str.count()` 數子字串** → 查 `path` 把 `filepath` / `pathlib` / `dispatch`
   全算進分母，灌成兩倍（2109 vs 1015）。改成字界（word boundary）比對。
2. **只報加總解析率** → 被通用名主導。改成中位數與加總並列。
3. **範圍過濾比對絕對路徑** → 專案根目錄自己就叫 `CodeSextant`，
   `--path-contains codesextant` 命中每一個檔，過濾等於沒作用、數字卻看起來像過濾過了。
   改成比對相對於 root 的路徑。這個最陰險——它不會報錯，只會靜靜地給你一個假數字。

**教訓：發布任何量測數字前，先證明量測方法本身是對的。** 方法錯會讓好工具看起來很爛
（第 1、2 坑），也會讓沒過濾的結果看起來像過濾過（第 3 坑）。抽查幾個你**確知答案**
的樣本是最便宜的驗證——本次就是看到 `classify_orphan` 12 個候選解出 10 個高信心（83%）
卻報總體 4.3%，才知道加總法有問題。

## 殘差誠實歸因

解不掉的部分不是零，它由三塊組成，不該混在一起講：

- **同名雜訊**：註解、字串、不同類別的同名成員——本來就不該算進來
- **動態解析**：反射、字串組出來的名字、DI 容器——靜態分析的**本質限制**，
  所有同類工具都一樣（Sourcegraph / CodeQL / Glean 全都有，學界稱為 "soundy"）
- **真的沒解出來**：這才是可以改進的部分

⛔ 差別從來不在「誰不會漏」，而在**漏的時候會不會講**。CodeSextant 每次查詢都在
`reliability` 欄位講；這份基線是把同一件事做到整個 repo 的層級。

## 已知不足

- 只量了 CodeSextant 自己。要能跟別人比，得在公認的開源 repo 上跑同一套方法。
- TypeScript 每符號 25 秒（走 ts-morph 子行程），比 Python 的 0.29 秒慢兩個數量級。
- 抽樣 25 個，統計上偏小；`--sample` 可調大，代價是線性變慢。
