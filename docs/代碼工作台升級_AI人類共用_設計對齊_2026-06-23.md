# CodeSextant → AI＋人類共用代碼工作台：設計對齊

## 〇、一句話

user 要把星圖從「看的 PoC」升級成「找該修的代碼 + 看完整代碼 + 編輯 + 版本時間戳」的工作台。**大部分能力 CodeSextant 已有**（找問題的引擎），缺的是三塊：動態出圖、git 版本/churn 維度、編輯層。其中「直接編輯」**跟 CodeSextant 唯讀導航圖鐵律衝突**，是必須 user 拍板的身分級分叉。

## 一、業界怎麼做（謙遜研究、決定方向）

| 工具 | 做法 | 對我們的教訓 |
|---|---|---|
| **CodeScene** | 不寫代碼、只分析；核心＝**Hotspot＝複雜度 × git 變更頻率(churn)**「複雜又常改才真痛」 | ⭐ 黃金公式：找該修的代碼＝複雜度 × churn。把 user 要的「版本/時間戳」和「找問題」一石二鳥 |
| **Sourcegraph** | 代碼搜尋＋導航，**編輯跳回 IDE**（不在自己平台編輯）＋協作註解 | 編輯走「跳 IDE」是主流、乾淨 |
| **Sourcetrail** | 純本地符號跳轉/圖瀏覽——**2021 停更** | 純看難獨活（呼應 CodeSextant 賽道教訓） |
| **CodeSee** | 自動地圖、每次 merge 更新、變更影響視覺化——**已收掉** | 純視覺化也死；要綁「找問題」才有命 |
| **CodeCharta** | 開源、代碼→互動 **3D 代碼地圖**、視覺化複雜度/技術債/hotspot | CodeSextant 星圖同路線、開源可借鑑 |
| **CODESTRUCT / codebase-digest** | AI agent 用 **結構化(AST/符號)** 表示代碼、非 flat text | AI 友善＝結構化接口；人類友善＝視覺。共用引擎、兩前端 |
| **ops-codegraph-tool** | function 級依賴圖、34 語言、**MCP server for AI**、複雜度、git diff impact、co-change、本地零 key | 幾乎是 CodeSextant 競品；證明「本地+AI接口+git」路線成立 |

**三條硬結論**：①「找該修的」用 Hotspot（複雜度×churn），git 不只是版本、更是找問題的維度；②純看會死，要綁「找問題」；③編輯業界都「跳 IDE」、沒人在地圖內直接編輯成功——user 要直接編輯＝逆主流、需謹慎分層。

## 二、架構（引擎一份、兩種前端、編輯分層）

```
            ┌─────────────── CodeSextant daemon（引擎核心，大部分已有）───────────────┐
            │ 抽符號 / 找引用(jedi·ts-morph) / 認知複雜度 / health / 死碼 / 重複 /     │
            │ 呼叫鏈 / 爆炸半徑   ＋【新增維度：git churn＝變更頻率＋時間戳＋blame】     │
            │   → Hotspot 排序（複雜度 × churn）＝「最該修的代碼」                       │
            └───────────────┬───────────────────────────────┬───────────────────────┘
                            │ 結構化 API / (未來)MCP          │ /graph_data 出圖 API
                  ┌─────────▼─────────┐            ┌──────────▼──────────┐
                  │  AI 接口（給代理） │            │ 人類接口（星圖 GUI） │
                  │ 問「哪些該修」→拿  │            │ 選 repo→出圖·節點顏色 │
                  │ hotspot+完整代碼  │            │ 標 hotspot/health·點  │
                  └───────────────────┘            │ 節點看完整碼+git歷史  │
                                                   └──────────┬──────────┘
                                                   ┌──────────▼──────────┐
                                                   │ 編輯層（分叉、見§三） │
                                                   └─────────────────────┘
```

## 三、核心分叉（要 user 拍板）

**分叉 1（最重要）＝「直接編輯」怎麼做**——這條動到 CodeSextant「唯讀導航圖」鐵律：

| 選項 | 做法 | 守鐵律? | 業界 | 我的評估 |
|---|---|---|---|---|
| A 推翻鐵律 | 星圖內嵌全功能編輯器、直接改檔存檔 | ❌ 推翻 | 無成功先例 | 風險最高、毀導航圖純粹性 |
| **B 分層（建議）** | 星圖核心保持唯讀「找問題」；點節點→**內嵌輕量編輯器**改該符號/檔→存檔→git commit。編輯是「附加模式」不污染導航 | ⚠ 分層保留 | 接近 Sourcegraph | 兼顧：守住「找問題」純粹、又能改 |
| C 跳 IDE | 點節點→在 VS Code/Cursor 開該位置編輯 | ✅ 完全守 | 主流 | 最省力、但「不是直接在這編」 |

→ **我建議 B**：導航/找問題那層永遠唯讀（CodeSextant 身分不變），編輯是疊加的獨立模式（內嵌 Monaco 之類輕編輯器），改完寫回檔＋git。這樣「AI 看結構化、人類看星圖找問題、要改點開就改」三者並存，鐵律只在「找問題層」守、不擋編輯。

**分叉 2＝版本/時間戳**：⭐ **接 git，不自造輪子**。git 已是版本控制；接 `git log`/`blame` 給每個符號：最後修改時間、變更次數(churn)、誰改的、歷史 diff。**churn 同時餵 Hotspot**（一石二鳥）。非 git 的 repo 才退化成「無版本維度」。

**分叉 3＝「所有代碼都在裡面+整理好」**：節點帶**完整符號代碼**（現在只 34 行片段→改成完整函數/類別本體）＋點檔案看整檔；「整理好」＝按社群/檔案樹/hotspot 三種視圖切換。

## 四、CodeSextant 已有 vs 缺（離目標多近）

| 願景要素 | 狀態 |
|---|---|
| 找問題代碼（複雜度/health/死碼/重複/未接線） | ✅ **已有**（引擎成熟） |
| 完整代碼在裡面 | 🟡 半有（現帶 34 行片段，改帶完整本體即可） |
| 代碼地圖視覺化 | ✅ 已有（星圖 v3、剛修好帶代碼） |
| 動態選 repo 出圖 | ❌ 缺（接 daemon /graph_data 端點＝正路核心） |
| git 版本/時間戳/churn | ❌ 缺（接 git log/blame，新維度） |
| Hotspot（複雜度×churn 找最該修） | ❌ 缺（churn 補上即可組合，引擎已有複雜度） |
| 編輯 | ❌ 缺（分叉 1 拍板後做） |
| AI 結構化接口 | 🟡 半有（daemon 已有 get_map/get_health 等 API，未來可包 MCP） |

→ 結論：**引擎地基已成熟，缺的是「動態出圖 + git 維度 + 編輯層」三塊接線**，不是從零。

## 五、分階段落地序（P0 立即可開工、不碰鐵律）

- **P0（不碰鐵律、立即價值）**：① daemon 加 `/graph_data?project=` 端點（把 build_repo_graph+group_in_box_v3+完整代碼 整合進引擎，前端選 repo 即時出圖）② 節點帶完整代碼 ③ 三視圖（社群/檔案樹/hotspot）。**做完＝能選任意 repo、看完整碼、找 health 熱點**。
- **P1（git 維度）**：接 `git log/blame` → 每符號 churn+時間戳+最後修改者；Hotspot＝複雜度×churn 著色（星圖飽和度/紅度）。**做完＝一眼看出「最該修的代碼」**。
- **P2（編輯層、需分叉 1 拍板）**：依 user 選的 A/B/C 做編輯（建議 B 內嵌輕編輯器→存檔→git commit）。
- **P3（AI 接口強化）**：daemon 包 MCP server，AI agent 直接問「哪些該修/問題代碼」拿結構化 hotspot+完整碼。

## 六、自我紅藍（風險先攤開）

- **R1 編輯毀身分**：若選 A，CodeSextant 從「乾淨唯讀導航圖」變成「又一個半吊子 IDE」，競爭力盡失（Sourcetrail/CodeSee 都死於不夠專注）。→ 建議 B 分層，導航層守唯讀。
- **R2 即時佈局慢**：大 repo 即時跑 spectral+louvain 佈局可能數十秒。→ P0 加快取（同 repo 同 git sha 重用佈局）＋背景預算。
- **R3 churn 跨 repo 不可比**：churn 絕對值受 repo 年齡影響。→ Hotspot 用 repo 內相對排序、非絕對閾值。
- **R4 完整代碼撐大 json**：節點帶完整本體，大 repo json 暴肥。→ 列表只帶摘要、點節點才按需抓完整碼（daemon `/symbol_code?path=&line=`）。
- **R5 「不管邏輯」要守住**：所有標記（hotspot/health/死碼）是「值得讀碼複核」線索、永不出「應改/應刪」決策——守 CodeSextant 鐵律③，編輯由人/AI 決定、工具只導航。

## 七、是否跑正式紅藍 CBUA
本檔＝主代理謙遜研究＋自我紅藍的設計對齊草案。若 user 要更強對抗（尤其分叉 1 編輯身分決策），可再跑正式紅藍 CBUA Workflow 強化——但會 fan-out 子代理、有 529 風險，建議 user 明確要才開。
